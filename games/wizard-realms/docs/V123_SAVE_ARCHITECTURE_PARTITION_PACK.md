# V123: wizard save-memory architecture partition

## Outcome

Preserve the full checked V33 save contract while reducing the transient memory cost of authentic migrated saves enough to resume the guarded Mireglass discovery, save/reload, and two-way fairy-ring journey. The V122 client adapter proof halved pre-read clones but did not lower peak renderer RSS. Therefore this pack starts with architecture and migration analysis, not more adapter micro-optimizations. User-facing V32 preview stays on 5193; V33 development preview stays on 5194. No GitHub, commit, rollout, or save-data mutation is authorized. Private checkpoints remain mode 600/700 and must never be printed or packaged. Only one automated browser renderer may run at once.

## Measured baseline and constraints

In the authentic U5 no-Canvas V33 twelve-W-frame save, baseline-adjusted renderer RSS rose 347,296 KiB after V121-C1. V122's one-use V30-to-V33 client proof cut pre-read clone calls by 52.2% and V23/V17 canonical validations by 61.0%, yet the adjusted rise was 352,240 KiB. The authoritative flow and store still read twelve version databases, decode full nested V33/V32-to-V17 ancestry, check exact source pinning, replay the witness, validate a checked successor, and do CAS. Native IndexedDB get/put calls were brief in V121-B4; post-fetch decode/proof and candidate phases were expensive. JS heap and RSS peaks need not align due GC. No specific single allocation site accounts for all bytes.

The existing local save format is trusted only as a *consistency-checked local record*, not as an unforgeable anti-cheat source. Any new partition must retain at least the current anomaly rejection: no fabricated progress, aliases, invalid descriptors/prototypes, stale revisions, cross-slot mutation, or source swapping. Saving and resuming old V17-to-V33 profiles must remain possible through an explicit migration or read compatibility layer. In-memory process isolation alone is not enough if total RAM usage or durable integrity worsens.

### B: migration and security contract

Define how an old V33 checkpoint migrates to any new compact save without rewriting or deleting the source, how live V32-to-V17 ancestry is pinned, and how save/reload/rollback/CAS and action replay remain strict. ### C: runtime and browser budget review

Read-only. Determine whether V122's client proof should be retained as a measured latency optimization or removed to reduce code/security surface before the new save layer. Quantify what separate Worker/IndexedDB process would and would not solve. Plan a single-renderer benchmark with RSS, total process memory and end-to-end UI responsiveness, preserving V32 and visuals. No renderer yet.

### Decision gate

The primary agent selects one architecture only after A/B/C agree on a concrete storage and migration contract. Produce a bounded implementation ticket pack with files, test fixtures, red-to-green proof, parallel ownership, rollback strategy, and size tripwires before code changes. Do not fit a schema migration into a cosmetic diff. If all safe designs require a larger explicit product decision, report that clearly and ask the user, without declaring the durable game goal complete or blocked prematurely.

## Validation gates after a selected implementation

Require old V33 save continuation without mutation, fresh V33 start, forged/corrupt/revision/alias rejection, power-failure/partial-write recovery, TypeScript/build, focused domain/store tests, and independent security review. Then repeat the exact no-Canvas U5 twelve-W benchmark with a 1,024,000 KiB exact-PID guard and compare baseline-adjusted RSS, idle RSS, JS heap, save latency and total browser-process memory. A real UI renderer may be opened only after the no-Canvas save shows a substantial peak reduction and safety review passes. The UI gate includes bounded Mireglass discovery, save/close/reopen, two-way ring travel, post-arrival movement, and V32 regression check. Keep the preview available and close owned test renderers after each run.

## A/B/C result and selected first partition

The V33 lineage embeds a complete V32 root, which embeds V31 and older roots. V23-to-V33 checked reads currently co-materialize roughly 66–82 progress-head equivalents before decoder, proof and native copies. A normalized V34 archive is the strongest full storage candidate, but it requires an explicit schema migration and a new fail-closed downgrade rule; its peak-memory benefit is unproven while live ancestry must still be checked. A dedicated Worker may improve UI responsiveness but cannot be credited with lower total RAM or a separate OS process. V122's client proof reduced clone counts, not peak RSS; keep it only as a guarded baseline and do not make a future schema depend on it.

Security review found a smaller same-schema architecture partition worth testing first: the ancestry is an adjacent checked chain. Simultaneous retention of every raw root is not semantically required. Under the existing lock, keep target V33 read/proof, validate older source pairs toward V32 one at a time, retain only the neighboring roots long enough for the current exact comparison, and return the same checked start/receipt. Every source must still use full `readChecked`, every existing edge comparator must remain unchanged, and the target/source blocked-reason precedence and all fail-closed outcomes must remain identical. Preserve V33 witness replay and CAS untouched. The memory effect remains uncertain because atomic stores cache raw/decoded roots and source-only reads create unused proof clones.

S1a's genuine U5 guarded no-Canvas save passed all correctness checks: twelve W frames, zero rejections, all twelve checked store reads, one V33 commit, and no Canvas. Renderer baseline was 279,024 KiB, peak 592,496 KiB, adjusted rise 313,472 KiB, and post-GC idle 309,040 KiB. That is an 11.0% adjusted improvement over V122's 352,240 KiB, but exceeds the 264,180 KiB gate by 49,292 KiB. Clone counts were unchanged (964 pre-read, 4,717 total). Whole-Chrome-tree RSS was measured for the first time, baseline 1,326,992 KiB and save peak 1,631,184 KiB, so cross-version total-process comparison is unproven. Browser/guard closed, private checkpoint unchanged, ports 5193/5194 HTTP 200. This is a safe same-schema improvement but **not a material RAM repair**; real UI traversal remains gated. The phase evidence argues against S1b V29/V25 streaming as the next move because the V29 segment contributes a small fraction of the remaining peak. Select a planned V34 normalized archive/compact live root next, dev opt-in only, with old V33 data untouched and independent migration/security proof before any rollout.
