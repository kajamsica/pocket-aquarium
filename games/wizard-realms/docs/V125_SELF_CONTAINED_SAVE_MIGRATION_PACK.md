# V125: self-contained V34 save migration, development preview

## Goal and decision scope

Make Wizard Realms' long-session single-player save path safe enough to complete the Mireglass fairy-ring journey, while preserving the existing V33 save and V32/V33 previews. The normal authoritative simulation remains checked by game rules. This pack proposes a **development-only, opt-in** V34 database and entry, not production rollout, GitHub work or deletion of an old save.

V121–V123 isolated the large transient allocation in the repeated checked save path. A read-only V33-to-V17 source check through the new V124 seam succeeded but took 14.07 seconds on the authentic U5 profile and still peaked at 520,784 KiB in a no-Canvas browser session. The V123 twelve-W save's baseline-adjusted renderer rise was 313,472 KiB, above the 25% improvement gate. The continuous source-pin V34 design would still read, decode and compare all legacy databases every save. Its tree archive was also proven incompatible with V33-valid shared-buffer saves; a graph archive could repair compatibility but has no measured hot-path advantage. Autosave-cadence changes do not remove the per-save cost.

## Explicit trust-model change

V34 validates a complete V33-to-V17 live chain **once** under the existing world lock during explicit migration. It then writes its own compact baseline and revision-zero head atomically in a separate `wizard-realms:world:v34` database. Subsequent V34 inspect, resume and save operations validate/replay/CAS **V34 only**. No prior-validation flag, hash-only acceptance or unvalidated import is allowed: the validated migration output becomes V34's new baseline. This stops detecting later mutation or deletion of legacy databases and differs from V33's continuous ancestry check. For an opt-in single-player preview, that is an intentional tradeoff in favor of playability, not a claim of anti-tamper security.

V33 remains byte-for-byte untouched and playable as its own older branch. No automatic fallback, rewind, merge or downgrade from a nonempty V34 target is permitted. If a player later advances V33, the two previews can diverge; the V34 UI must say so clearly. A corrupt V34 target blocks and offers only an explicit recovery choice that warns later V34 progress could be lost. Production activation requires a separate dual-version fence/conflict/recovery policy and user-facing migration decision. Separate databases cannot provide a cross-database atomic CAS against an uncooperative old client; the shared world lock covers cooperating current clients during migration.

## Target representation and authority

Prefer one `records/root` IDB record initially, with an exact versioned envelope:

- `lineage`: origin `v33-migration`, seed/rules profile, source V33 revision, and an owned compact `genesis` gameplay progress copied from the fully checked current V33 head. No V33/V32-to-V17 root or raw graph is stored.
- `head`: V34 schema/version, V34 save revision, canonical gameplay progress and witness.
- `previous`: null only at revision zero; otherwise the immediately prior V34 head.

The decoder enforces exact keys/types, an immutable migration baseline, valid progress through existing `decodePublicV31ActionProgress`, seed consistency, conservation from the compact genesis through `publicV32Preserves`, monotonic transition through `publicV32Monotonic`, exact previous/head revision relation, and checked `replayPublicV33Witness` equality. Reuse V33 witness decoding and action reducers, including fairy-ring travel, Highland, mining, building and Return Home. Do not trust a controller-returned progress object as persistence authority. V34's genesis is the *current V33 head at migration*, not V33's older V32 genesis; the V33 root decoder cannot validate this compact target directly.

The V34 store gives one-use proof tokens. A readwrite transaction checks the exact `root` keyset and full prior **gameplay value** (lineage, genesis, head, previous and revision) before writing a checked successor, so a stale or competing semantic writer cannot silently win. Match the V33 store's value-semantic CAS precedent, not a new graph-identity codec: alias topology in the old raw record is not part of V34 gameplay progress. A missing target permits only explicit migration. Any nonempty partial, extra-key, malformed or unsupported-version target blocks. Migration writes the entire revision-zero root in one strict transaction and leaves V33 unchanged if it aborts. A compact single-record schema avoids archive piece manifests and cross-piece identity, because raw V33 object identity is not retained after the checked migration.

Shared interface for parallel lanes: `publicWorldV34Snapshot.ts` exports `PublicV34Root`, `PublicV34Head`, `createPublicV34Root(sourceHead: PublicV33Head)`, `decodePublicV34Root(raw)` and `decodePublicV34CheckedSuccessor(before, raw)`. The new lineage stores `origin: 'v33-migration'`, a stable rules profile, seed, nonnegative `sourceRevision` from the V33 head, and a copied compact `genesis` progress. The V34 head uses its own schema, starts at save revision zero with null witness, and `previous` is null at genesis. `atomicV34Database.ts` exports `createAtomicV34Store(factory, name)` with V33-shaped `readChecked()` status/proof and one-use `commit(proof, next)` results. The flow lane owns `publicWorldV34Flow.ts` and any V33 checked-head seam change, not the snapshot/store files. Interface changes require a direct lane message before either side edits the other's files.

The V124 `withLockedCheckedPublicV33SourceRaw` seam may be reused for the one-time source check, but its generic callback exposes mutable raw data. The V34 migration adapter must extract only an owned checked V33 head and source revision within the lock, never return/retain/mutate the raw object, and avoid a second full V33 decode if practical. Any seam change must preserve ordinary V33 behavior and tests. All V34 operations use the same world lock exactly once, without nested V33 public calls.

## Implementation tickets and ownership

1. **Compact domain and store:** new V34 snapshot/authority/store files and focused synthetic tests. First make forged baseline, previous, head, witness, stale proof/CAS, extra record and atomic abort tests red. Implement strict decoder, checked successor and one-record transaction. Reuse V33 action rules rather than duplicating them.
2. **Migration flow:** new V34 flow/migration files and focused tests. Fully check V33 once under the existing lock, extract an owned current head, write V34 revision zero, and prove V33 bytes and revision remain unchanged. Test missing/partial/corrupt V34, valid V34 resume with every V33-to-V17 store unavailable, competing start, later V33 divergence and no silent fallback. Any V33 seam adjustment belongs to this ticket and must receive an independent regression review.
3. **Opt-in entry/controller:** new V34 entry and only minimal routing/controller adaptations. Behind a build-time experimental flag defaulting off, `?publicWorld=v34` is visibly labeled as a separate save branch. Missing target offers explicit copy/import; valid target resumes; corrupt/partial target blocks. Keep V32/V33 routes, camera, art and controls unchanged. A fresh V34 game start must ultimately be supported; the first authentic migration preview must not masquerade as that complete new-user path.
4. **Independent security and UI proof:** review exact authority, one-use proof, target CAS, migration abort, branch/recovery copy and lack of V33 mutations. Run focused tests, TypeScript and production build. Then one exact-PID guarded no-Canvas U5 migration and twelve-W save from a disposable checkpoint copy on its original `127.0.0.1:5194` origin. Require V34 adjusted renderer rise <=235,104 KiB, no higher post-GC idle or Chrome process-tree peak than a matched V33 baseline, and acceptable save latency. Only after that gate, run one WebGL renderer below the 1,024,000 KiB watchdog through Mireglass ring discovery, save/close/reopen, two-way travel and post-arrival play. Close owned test browsers after each proof; leave the user-facing previews live.

## Safety, scope and proof

Do not copy private U5 contents into source, fixtures, logs or PRs. Use synthetic fixtures for adversarial tests. Preserve all dirty/untracked worktree data. No commits, branches, PRs, pushes, deployment or production route switch are authorized here. Existing V32 and V33 save behavior is a regression gate. The new V34 format is not accepted because it compiles or opens a page; it must pass the authentic memory, replay, recovery and end-to-end gates above. If the no-Canvas gate fails, stop rollout and replan the measured owner rather than weakening checks further. The full-game objective remains active beyond this save repair.
