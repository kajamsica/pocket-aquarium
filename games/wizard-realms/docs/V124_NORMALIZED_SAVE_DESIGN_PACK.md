# V124: opt-in normalized Wizard save design

## Objective and authority

Design, then stage a development-only successor to V33 whose checked save has materially lower peak memory on an authentic migrated profile. This is necessary before the pending Mireglass fairy-ring UI journey. The existing V32 and V33 previews, databases and private checkpoints must remain untouched and playable. A new version may migrate by reading a fully checked V33 source and writing a separate database only after a complete atomic transaction; no in-place conversion, fallback rewind, source deletion or user-facing rollout is authorized. GitHub, commits, branches and deployment remain out of scope. Preserve all previously dirty files. A future production activation/downgrade policy is a separate decision after evidence.

## Why a new representation is being considered

V122's private adapter proof cut pre-read clone calls by 52.2% but did not lower peak RSS. V123's adjacent V33 source inspection improved adjusted RSS 11% to 313,472 KiB, still above its 264,180 KiB gate. In the real no-Canvas trace, V33 target read/decode and candidate/commit dominate; V29 ancestry inspection is a small fraction. V33 lineage embeds V32 and successively older roots, and the flow/store repeatedly materialize nested heads, proofs and CAS copies. More local adapter or V29 clone tuning is not justified by measured phase evidence.

## Design constraints

- No hash-only source pin or trusted prior-validation flag. Each save must recheck the complete live V33-to-V17 chain and exact migrated source against its anchor under the existing world lock, unless a separately approved trust-model change occurs.
- Store a fixed exact manifest and versioned, partitioned source anchor plus compact current head/previous/witness. Keep source pieces small enough to compare exactly with bounded segmentation. The archive must preserve descriptor/prototype and cross-piece object/backing identity that current V33 can accept; a tree-only alias rejection is insufficient. Preserve one-use proof, checked successor replay and in-transaction revision CAS.
- A missing target is retryable migration; any nonempty incomplete, extra-key, corrupt, stale or source-changed target blocks. A later valid V33 write must block the successor rather than silently rewind or merge. Old V33 data remains recoverable and byte-for-byte unchanged.
- Reuse the existing world lock and checked ancestry logic without nested lock acquisition. Do not duplicate twelve-store trust rules divergently. The V34 runtime may reuse V33 movement and visual projection, but persistence must be authoritative and independently replayed.
- No multiple automated renderers. No private checkpoint contents in logs, source, tests or PRs. Use synthetic fixtures for most tests; authentic U5 only in a guarded isolated browser after source review.

## Planning lanes before implementation

### A: normalized storage and copy graph

Read-only design. Specify exact IndexedDB record keys, archive piece shapes, manifest, genesis/head/previous representation, bounded exact comparison strategy and CAS transaction. Model object-copy peak and explain why it should be lower than V33's target read/candidate peak, accounting for repeated live ancestry reads and per-store caches. Define invalid/extra/partial record behavior and synthetic fixtures. If exact cross-piece alias proof cannot be achieved after separate writes, explicitly propose a safe pre-write ownership check and persisted canonical encoding, or stop.

### B: migration, flow and runtime contract

Read-only design. Specify how a fully checked V33 start is obtained once under the existing lock, how it is pinned in the new archive without mutating V33, how later live V33-to-V17 checks reuse the same source inspection, and how V33 controller/witness semantics are carried into the new compact root. Define start/resume/save, Return Home and fairy-ring action flows, stale/partial recovery and V33 downgrade rejection. Define a bounded module/API map.

### C: UI entry and test surface

Read-only design. Specify an opt-in `?publicWorld=v34` entry that cannot be mistaken for production V32/V33, separate browser/profile/port semantics, authentic U5 migration without source mutation, an identical no-Canvas benchmark, and only then a one-renderer Mireglass journey. Preserve V32 camera/graphics behavior and use synthetic tests first. No renderer yet.

### R: independent security challenge

Read-only. Attack the combined design: tampered archive, alias and descriptor normalization, changed live source at any version, partial migration, duplicate/extra keys, forged progress/witness, stale CAS, concurrent process ignoring lock, downgrade to V33, forged runtime reply and resource exhaustion. Require explicit limitations instead of claims of unforgeable local saves.

## Decision and implementation boundary

The primary agent must select a concrete A/B/C interface after R review and write implementation tickets with file ownership, migrations, red-to-green tests, rollback and size tripwires. No production edits from design lanes. Prefer vertical slices that can be independently validated rather than a single unreviewable schema rewrite. A new archive is not accepted merely because a schema exists; the authentic guarded no-Canvas save must show at least a 25% baseline-adjusted renderer peak reduction from V123's 313,472 KiB (target <=235,104 KiB), no higher idle or total-process memory, valid ancestry/replay/CAS, and reasonable latency. Only then run the real UI discovery/reload and two-way travel gates. If the no-Canvas memory gate fails, stop and reconsider representation or scheduling; do not ship V34.

## Design receipts and first implementation gates

The four read-only lanes agree on a conditional first slice, not on a RAM fix. The proposed V34 target is a separate `wizard-realms:world:v34` database with an exact fixed keyset: manifest, compact tip/control, tip/head, tip/previous, tip/witness, and bounded contiguous archive pieces of the V33 source. Migration writes the entire revision-0 target in one strict transaction and never changes V33. Every V34 operation checks the complete live V33-to-V17 ancestry, compares the live V33 source exactly to its archive, validates the compact target and checked witness, and uses a one-use proof plus in-transaction CAS over every relevant target record. Neither an archive hash nor a prior-validation flag substitutes for these checks. A missing target offers explicit retryable migration; a nonempty partial or corrupt target blocks instead of silently falling back to V33. V34 is a visibly experimental opt-in and does not change the V32 or V33 default. The authentic U5 migration must use its existing `127.0.0.1:5194` origin in an isolated profile.

The source archive must be a canonical, bounded, injective representation of the raw V33 object graph, preserving exact keys, descriptors, prototypes, typed-array bytes and repeated-reference/backing identity. Separate IndexedDB records cannot preserve cross-piece identity by themselves, so the canonical stream must assign stable graph IDs before segmentation. The authentic private V33 record was alias-free, but synthetic persisted roots accepted by V33 can contain aliases and shared backing; a tree format is **NO-GO**. Never silently reject a valid existing save or de-alias it before pinning. Oversized hostile IndexedDB values can still allocate during native `get`; the size budget is a best-effort bound, not an OOM guarantee.

The V33 source-read interface is the other gate. `atomicV33Database.ts` may expose `readRawSourceEnvelope()` that checks the exact single-record keyset and returns the one native IndexedDB value without cache or proof clones. `publicWorldV33Flow.ts` may factor its existing V32-to-V17 ancestry inspection into one private helper shared with ordinary V33 `inspectUnderLock`. A new `withLockedCheckedPublicV33SourceRaw(...)` obtains the same world lock exactly once, calls the existing `decodePublicV33Root(raw)` exactly once, verifies the decoded V32 source receipt against live ancestry, releases decoded/ancestor references, and invokes a bounded V34 callback with only the raw source. The new path must preserve V33's error priority and existing twelve-store trust rules; the codec's exact comparison is not semantic validation. Do not nest public V33 operations or add a divergent validator. This interface avoids V33 store cache/proof/candidate clones, but decoder allocation remains, so its RAM benefit is only a hypothesis.

### Slice 0: authentic source-shape preflight, read-only

Owner: isolated UI/performance probe. From an unchanged copy of U5, on the original 5194 origin, open one minimal no-Canvas document, read only V33 `records/root`, and traverse the returned object graph without emitting values. Report counts of distinct objects, repeated references, cycles, shared typed-array backing buffers, non-ordinary prototypes, non-default descriptors, symbols, sparse arrays and approximate node/byte bounds. Bind the exact renderer PID and 50 ms RSS watchdog before the read; stop the owned browser below 1,024,000 KiB and close it afterward. Never print or modify the checkpoint or save. A failed/near-cap probe is inconclusive, not proof that aliases are absent.

### Slice 1: source-read seam, parallel to Slice 0

Owner: V33 store and flow implementer. Only `atomicV33Database.ts`, `publicWorldV33Flow.ts` and focused synthetic tests. Add the above source-read callback and factor ancestry comparison without changing existing V33 public method behavior. Red-to-green tests cover exact target keyset, missing/invalid/storage errors, full live source chain and status precedence, valid V33 source, changed V33/V32 and deeper ancestors, and one lock with no nested call. Focused tests, TypeScript, build, diff check and independent source/security review are required. No browser, real save, V34 database, entry route, GitHub action or commit.

### Slice 2 and later, gated

Slice 0 proved only that the authentic U5 graph itself can be encoded; a separate compatibility challenge ruled out the restricted tree design for the complete V33-valid-save surface. After Slice 1 review, specify a graph-ID canonical codec, record budget and comparator with synthetic adversarial red-to-green tests. Then build the separate V34 store/flow, followed by an opt-in entry. Do not treat the format as accepted until the authentic no-Canvas twelve-W benchmark meets <=235,104 KiB baseline-adjusted renderer rise, does not raise idle or process-tree memory, and preserves checked save behavior. If that gate fails, pause V34 rollout and plan an equivalent streaming validator or different scheduling/representation. Real WebGL UI traversal remains closed until then.

## Slice 0 receipt and scheduling fallback

The guarded read-only U5 preflight passed for this authentic V33 root. Its IndexedDB-returned graph had 11,506 distinct objects, zero repeated-reference edges, zero cycles and zero shared backing-buffer groups. It had 13 typed-array views with distinct backings, no unknown prototypes, non-default descriptors, symbols or sparse arrays. The exact renderer peaked at 571,584 KiB below an 870,400 KiB early-stop guard; the sole owned browser and watchdog were closed, the private checkpoint remained unchanged, and both previews returned HTTP 200. This establishes that a tree archive can represent **this** save, not that the codec is correct for every valid source or that V34 is memory-safe.

A second, separately guarded read-only census found zero `undefined`, bigint, symbol, function, non-finite number or negative-zero values in that source. Its only built-ins were 13 full-backing, zero-offset `Uint8Array` views and their distinct 32,768-byte `ArrayBuffer` backings. The renderer peaked at 541,264 KiB; the owned browser closed and the checkpoint was unchanged. A codec restricted to plain objects, dense arrays and full-backing byte arrays is therefore compatible with this authentic source, but migration of every possible V33-valid save remains unproven. Do not equate a V33-valid root with a codec-supported tree without explicit tests or a reviewed migration-refusal policy.

An independent read-only scheduling review found no credible autosave-cadence fix. The current controller saves pending movement when input goes idle and at 64 grounded frames, about 3.2 seconds of normal held play. The spike occurred after about 0.25 seconds of movement, and a checked read-only inspect alone incurred large transient memory. Shorter batches repeat the same decode cost; longer batches increase unsaved progress and eventually meet the 128-frame movement cap. No cadence change is authorized as a substitute for the measured save repair.

## Slice 1 source-read seam receipt

The V33 source-read seam is implemented in the existing untracked `atomicV33Database.ts`, `publicWorldV33Flow.ts` and their two focused test files, with no V34 database or entry change. The raw store method reads the exact single `records/root` envelope without making a V33 cache or commit proof. The new flow callback takes the existing world lock once, uses the same V32-to-V17 ancestry helper as ordinary V33 inspection, decodes the raw V33 root once and compares its V32 source receipt before invoking the consumer. Ordinary V33 witness, replay, CAS and public inspection behavior are unchanged. Red-to-green evidence: three seam tests and two raw-envelope tests initially failed on missing exports/methods; focused flow 6/6 and raw-envelope 2/2 passed after implementation, as did TypeScript, production build and whitespace checks. Independent source review found no ordinary V33 regression and issued GO for this seam, **not** for a V34 RAM claim.

Integration tripwire: the generic callback API does not freeze or confine the mutable raw object. A V34 consumer must encode and compare within the locked callback, not retain, mutate or return the source; it must never treat the raw envelope's `valid` status alone as semantic validation. The seam still allocates one full V33 decode and a native IndexedDB clone, and its authentic memory benefit is unmeasured. A separate guarded read-only no-Canvas seam probe is next. The proposed restricted codec also needs proof that every V33-valid persisted source fits its domain, or a reviewed graph-aware/expanded encoding; U5 alone cannot establish universal compatibility.

The guarded U5 no-Canvas read-only seam probe passed its correctness and resource guard: one V33 raw read, one checked read of each V32-to-V17 source store, one boolean-only callback, zero Canvas and no write. Its call took 14.07 seconds, renderer session peak 520,784 KiB and post-GC idle 301,168 KiB; renderer PIDs rotated, so baseline-adjusted savings are not comparable to V123. The owned browser/watchdog closed and the private checkpoint remained unchanged. This is **not** the V34 save-memory gate and raises a latency concern for later matched testing.

The compatibility audit then produced a decisive counterexample to the restricted tree codec: an otherwise valid V33 root can reuse the same state object in `head.state` and `lineage.sourceReceipt.head.state`. IndexedDB preserves that shared reference within the single record; both `decodePublicV33Root` and `createAtomicV33Store().readChecked()` accept it because they validate values without a global alias rule. A second synthetic root with two equal mask views sharing one `ArrayBuffer` is also accepted after fake-IDB put/get. The ordinary writer canonicalized the tested object alias, but direct persisted records accepted by the current reader are part of the compatibility surface. Therefore **exact-tree/v1 is NO-GO as the V34 archive** if all V33-valid saves must migrate. A graph-ID encoding preserving object and backing-buffer identity is now required; no alias-free-only migration or silent de-aliasing is approved. Slice 2 implementation remains gated on its exact format, independent challenge and bounded memory design.
